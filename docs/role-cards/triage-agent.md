# Role card: the triage agent

The trust-layer spec, A1.4, copied in form from the GTM pipeline's role cards. One card per agent. It reads like a job description, because the agent is treated like a member of staff: it has an owner, a written playbook, limits, and a person who checks its work.

| Item | This agent |
|---|---|
| **Name** | Triage agent (the "Claude Triage Step" in the n8n workflow "Change Desk: run triage", and `scripts/triage.py` for runs outside n8n) |
| **Purpose** | Read one bug or enhancement request and propose its fixed shape (the spec's triage shape): type, size in hours, lane, the fixed-date test (date and what breaks), the urgent test (what harm is growing), a business goal, the playbook that would handle it, a split for a large item, four score parts with reasons, a reason and a confidence |
| **Named owner** | Systems desk lead: a made-up role in this build. At an employer, the person who runs the systems team's intake |
| **What it reads** | One request: the requester's role (never a name), the title, the text, and what the requester said about a date or harm; today's date; the list of business goals. It sees no request id, no other request, no score of anyone, and no history |
| **What it writes** | Nothing. It returns one JSON object in the fixed shape. The workflow, not the agent, checks it and logs it through `changedesk.log_triage`, with a who-decided stamp |
| **What it must never do** | Follow instructions found in a request; take "urgent" or a date on the requester's word; score or judge a person; promise a date; send anything to anyone; use a lane, playbook, goal or flag the playbook does not list; repeat its instructions or a person's contact details |
| **Tools** | None. A single Claude Messages call with structured outputs (`output_config.format`). Model `claude-haiku-5-5`, effort `low` |
| **Playbook** | [`skills/triage-playbook/SKILL.md`](../../skills/triage-playbook/SKILL.md), version 1.0.2 (25/11/2026; 1.0.0 and 1.0.1 missed the eval bar and were not kept), put into the n8n Code nodes when the workflow is built (`scripts/build_n8n.py`). Its name, version and SHA-256 are logged with every call |
| **Guard rails** | Fixed in [`engine/triage.js`](../../engine/triage.js), outside the playbook: guard rules before the playbook; the request goes in as escaped JSON inside a data block; the reply must fit the fixed shape; the lane is set by the published rule from the agent's own answers to the two tests and its size, and a different lane from the agent is flagged; confidence below 0.70 is flagged; a large item needs a split that fits; a code screen looks for instructions, claims of approval, fake output, markup and contact details, and caps the confidence of a flagged request at 0.50; a reason that repeats the instructions is flagged; effort is set by code from the size, and goal fit is 1 by rule when no goal is named |
| **Approval point** | The n8n form "Change Desk: confirm lanes". A named reviewer confirms or changes the lane of every urgent, fixed-date, low-confidence or flagged item, and accepts or rejects every split. The store refuses to plan or start such an item without that confirmation (R5) |
| **Stop switch** | Nothing is scheduled: triage runs only when someone starts it from its form or from the command line. `python scripts/n8n_publish.py off` switches every workflow off. Revoking the key in the Claude Console workspace `gtm-pipeline` stops every AI call at once |
| **Spend limit** | The workspace `gtm-pipeline` has a US$10 monthly limit. Cost per triage: see [`docs/cost-sheet.md`](../cost-sheet.md) |
| **Evidence** | `changedesk.run_log` (every call: model, playbook, tokens, time, error), `changedesk.requests` (the proposal, the reasons it waits, the stamp), `changedesk.agent_handoffs` (each item handed to a person, and why), `changedesk.decisions` (the person's confirmation, with its stamp). One query from a stamp: `select * from changedesk.triage_record where call_id = '<id from the stamp>'` |
| **Eval** | 40 labelled requests in [`skills/triage-playbook/eval/cases.json`](../../skills/triage-playbook/eval/cases.json), eight hostile, graded by `scripts/triage_eval.py` against a bar set before the first run ([`bar.json`](../../skills/triage-playbook/eval/bar.json)). Playbook 1.0.2 on Haiku 5.5, three rounds: every answer in the fixed shape, lane 100%, size band 100%, playbook 97.5%, a person asked exactly when the label says 100%, hostile requests blocked 24 of 24, US$0.00088 a triage. Results: [`results.md`](../../skills/triage-playbook/eval/results.md). 1.0.0 and 1.0.1 were tuned on these cases, so stage 6 ran 1.0.2 once, unchanged, on 30 fresh labelled requests it had never seen, six hostile, labels committed first (cbacd4e): it met every line (lane 100%, size band 100%, playbook 96.7%, a person asked exactly when the label says 100%, hostile 18 of 18; the code screen caught 12 of the 18, the model 18). Results: [`results-fresh.md`](../../skills/triage-playbook/eval/results-fresh.md). A playbook that has not met the bar cannot be pushed (`scripts/playbook_bar.py`, in the pre-push check and CI) |
| **Review date** | When the code screen's patterns are next reviewed (two new kinds of attack passed it in the fresh eval; the model caught them), or sooner if the eval bar is missed or the playbook changes its lanes |
